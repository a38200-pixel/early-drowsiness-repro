- 앞 항목에서 기준 사건 6건의 개별 시각을 재현 로그에서 얻지 못했고, 사용자 표도 전달되지 않았다. 대신 사용자가 **구간별 사건 수**를 확인했다(2026-10-06): 0:12~0:19 = 1건, 0:45~1:05 = 2건, 1:09~1:22 = 3건, 합 6. 이 건수는 SVM 기록에서 도출했고 사용자가 2026-10-05에 육안으로 본 것과 같다고 확인했다. 규칙 가지의 결과와 무관하다. [확실] (사용자 확인)

### A. 재현 트랙의 기존 회전 구현과의 대조 (읽기만, 수정 없음)

- 기존 정의(`src/repro/orientation_common.py`): 방향 이름 "0", "cw90"(시계 방향 90도), "180", "ccw90"(반시계 방향 90도). `rotate_frame`은 `cv2.rotate`에 `ROTATE_90_CLOCKWISE`, `ROTATE_180`, `ROTATE_90_COUNTERCLOCKWISE`를 넘긴다. `reproduction_blink_headless.py`의 `--rotate none|cw90|ccw90|180`은 `frame = imutils.resize(frame, width=450)` 한 곳을 `imutils.resize(cv2.rotate(frame, ...), width=450)`로 치환해 원본 프레임을 먼저 회전한 뒤 같은 리사이즈를 한다(`build_replacements`의 107~109행). `survey_orientation.py`도 같은 `rotate_frame`으로 방향 4가지의 얼굴 수를 센다(`count_by_orientation`). 기존 방향은 영상의 회전 태그를 읽은 값이 아니라 사용자가 지정하는 값이다. ## 정정: 경보음 재생 방식 (같은 날, 사용자 청각 확인용, 규칙과 화면 표시 변경 없음)

- 정정(사실): 바로 위 보강의 재생 방식(`winsound.PlaySound(바이트, SND_MEMORY | SND_ASYNC | SND_NODEFAULT)`)은 winsound 문서상 `SND_MEMORY`와 `SND_ASYNC`를 함께 쓸 수 없어 `RuntimeError`를 일으킨다. 이 환경(Python 3.6.13)에서 같은 조합을 한 번 호출해 `RuntimeError: Cannot play asynchronously from memory`를 확인했다(소리가 나기 전에 예외로 끝나 재생되지 않았다). 그 구현은 재생 실패를 무시했으므로 소리가 조용히 나지 않았을 것이다. 위 보강의 "새 알람이 나면 처음부터 다시 재생(새 비동기 재생이 이전 소리를 대체)"와 "`PlaySound(None, SND_PURGE)`로 즉시 정지" 서술은 이 정정이 대체한다. [확실] (측정)
- 새 재생 방식: 사이렌을 0.25초 조각 둘(880 Hz 조각, 1320 Hz 조각)로 나누어 각각 유효한 WAV 바이트(헤더 포함, 16비트 모노 44100 Hz, 진폭 약 95%)로 만들어 캐시한다. 전체 3.0초 바이트는 조각 12개를 번갈아 이어 붙인 값과 같다. 알람마다 데몬 스레드를 하나 시작하고, 스레드는 두 조각을 번갈아 총 3.0초 동안 조각마다 `winsound.PlaySound(조각, SND_MEMORY와 SND_NODEFAULT)`를 `SND_ASYNC` 없이(동기) 호출해 재생한다. `SND_ASYNC`, `SND_PURGE`, `SND_LOOP`는 쓰지 않는다. 메인 영상 루프를 막지 않는다. [확실]
- 정지와 교체: 재생 스레드는 조각 사이마다 정지 신호(세대 번호)를 확인한다. R 키, m 키(음소거로 전환), q 종료, 새 알람이 정지 신호를 올리면 현재 조각이 끝난 뒤(최대 0.25초) 멈춘다. 새 알람은 이전 재생을 정지시키고 새 스레드를 시작하며, 새 스레드는 이전 스레드의 현재 조각이 끝나기를 기다린 뒤 재생해 소리가 겹치지 않게 한다(그래서 새 알람의 소리가 최대 0.25초 늦게 시작할 수 있다). 같은 갱신에서 여러 임계값의 알람이 나도 스레드는 하나만 시작한다. [확실] (코드)
- 실패 처리: 재생 중 예외가 나면 그 스레드를 끝내고 프로세스당 한 번만 콘솔에 `sound error: <예외 이름>: <메시지>` 한 줄을 출력한다(파일에 쓰지 않는다). 화면 표시와 규칙은 그대로이고 화면 구석 표시는 `sound: error`(빨강)가 된다. Windows가 아니면 소리 없이 동작한다. `--beep`, `--beep-all`, m 키는 그대로이다. [확실]
- 시험: 기존 3.0초 사이렌 시험을 조각 기반으로 바꾸고(조각이 유효한 WAV 헤더와 0.25초 길이를 갖고 전체가 조각 12개와 같음) 두 시험을 더했다. 가짜 winsound(실제처럼 두 플래그가 함께 오면 `RuntimeError`)로 `PlaySound` flags에 `SND_ASYNC`와 `SND_MEMORY`가 함께 들어가지 않고 같은 갱신의 두 알람에도 조각 12개만 재생되며 정지 신호 뒤 다음 조각이 재생되지 않음을 확인했고, 가짜 `PlaySound`가 예외를 던지면 콘솔에 한 줄만 나오고 `sound: error`가 되며 규칙 알람 시각은 일괄 재생 결과와 같음을 확인했다. 실제 소리는 재생하지 않았다. 전체 단위시험 215개가 통과했고(실패 0, 건너뜀 0) E-02 영상 2의 덤프 대조도 다시 일치했다. [확실] (측정)
- 소리는 메모리 조각 재생을 스레드에서 동기 호출(`SND_ASYNC`와 `SND_MEMORY`는 함께 쓸 수 없음)하고, R, m, 새 알람에서 최대 0.25초 안에 정지하며, 실제 음량과 정지 동작은 미검증이다. [미검증]
- 미검증: 실제 음량과 들림, 조각 사이의 끊김 소리(조각마다 재생 호출을 하므로 짧은 무음이나 딸깍 소리가 날 수 있음), 영상과의 끊김(스레드가 영상 루프를 막지 않는지), 정지 지연(최대 0.25초라는 가정), 실제 환경에서 새 알람이 이전 재생을 대체할 때의 동작, `sound: error` 표시. [미검증]

## 사람별 정규화 조사 결과 (읽기 전용, 2026-10-07)

조사 대상은 `third_party/ghoddoosian/Preprocessing.py` 전체(1~274행)와 `Training.py` 395~453행이며 파일은 수정하지 않았다. 아래는 코드 사실만이고 판단은 쓰지 않았다. [확실] (코드 읽기)

1. 정규화는 2단계이다. 1단계는 사람별 z-점수(`Preprocessing.py`의 `gen` 42~135행과 `Preprocess` 139~259행이 같은 코드를 중복해 가진다. 아래는 `gen` 기준 줄 번호이고 뒤쪽 `Preprocess`는 그 +112행 부근이다), 2단계는 학습 윈도우 전체의 표준화이다(`Training.py` 420~431행).
2. 1단계 통계는 alert.txt의 **마지막 1/3 깜빡임(개수 기준)**의 `np.mean`과 `np.std`(ddof=0)이다. `bunch_size = blink_num // 3`(56행, `Preprocess` 168행), `Freq[-bunch_size:]` 등으로 4개 특징(Freq, Amp, Dur, Vel, 읽는 열은 1~4, 51~54행) 모두 같은 방식이다(평균 59, 63, 67, 72행, 표준편차 60, 64, 69, 73행). 표준편차가 0이면 alert 전체의 `np.std`로 대체한다(61~62, 65~66, 70~71, 74~75행). 변환은 `x_norm = (x - u) / σ`(12, 14, 16, 18행)이다. 변환 대상은 alert의 **앞 2/3**(`remained_size = blink_num - bunch_size`, 57행, `normalize_blinks(remained_size, ...)` 77행)과 semisleepy 전체(98행), sleepy 전체(116행)이며, 각 사람이 자기 alert의 통계를 쓴다. 기준으로 쓴 뒤 1/3은 alert 샘플에서 빠진다. 뒤 1/3으로 한 이유는 코드에 없다(56행 주석은 "one third used for baselining"뿐).
3. 2단계는 학습 윈도우 전체(`Blinks[:,:,k]`, 모든 윈도우와 시간 스텝)의 `np.mean`과 `np.std`로 4개 특징을 같은 방식으로 표준화한다(`Training.py` 420~431행). 학습 통계를 테스트에도 적용한다. 통계에는 세 레이블(alert, semisleepy, sleepy)의 윈도우가 합쳐져 있고(127~128행), 보폭 2와 윈도우 30의 겹침과 짧은 파일의 패딩 0도 들어간다(`unroll_in_time` 24~40행, 실행부 263~264행). 이 평균과 표준편차를 저장하는 코드는 읽은 범위(395~453행)에 없다(미확인).
4. 기준 구간의 깜빡임 수를 확인하는 코드는 없다(`Preprocessing.py` 1~274행에서 찾지 못함). 10개 미만 규칙은 저자 코드가 아니라 이 프로젝트의 B1 정책이다(사용자 정리). 개수가 적을 때 코드가 하는 일은 `unroll_in_time` 27~30행의 앞쪽 0 패딩(30개 이하일 때 윈도우 하나)과 표준편차 0일 때의 대체뿐이다. blink가 0~2개이면 `bunch_size`가 0이라 `Freq[-0:]`가 파일 전체가 된다(언어 동작이며 보호 코드는 없다). [확실]
5. Freq(alert.txt 열 1)는 세션 시작부터의 누적 비율이다: `TOTAL_BLINKS / number_of_frames × 100`이며 `number_of_frames`는 얼굴이 검출된 프레임 수이다(추출기 복제본 `blink_video_dump.py` 407, 485, 494행, 추적 분기 569, 576행). Dur(열 3)는 프레임 수이다: `duration = end - start + 1`(복제본 185행). 원본 `blink_video.py`의 줄 번호는 이번에 읽지 않았다. [확실]
6. `Preprocessing.py`는 262~272행(`Preprocess` 호출 268행)이, `Training.py`는 408행 이후의 반복문이 최상위에서 바로 실행된다. import하면 실행되므로 필요한 함수(`normalize_blinks`, `unroll_in_time`)는 복사해서 써야 한다. [확실]
7. 미확인: `Training.py` 1~394행과 454행 이후, 원본 `blink_video.py`의 줄 번호. [미검증]

# 라이브 데모 처리 속도 진단 결과 (2026-10-09)

이 항목은 `live_demo.py`의 처리 속도 진단 결과를 기록한다(DECISIONS.md I-W-21). 코드와 테스트는 바꾸지 않았고 새 측정도 하지 않았다. 현재 측정(A)과 이전 측정(B)의 숫자는 사용자 보고(화면에서 눈으로 읽은 값, 3초 창 평균)에서 옮겼고, 4번의 숫자는 이전 읽기 전용 측정의 대화 보고(원자료)에서 옮겼다. 경로는 쓰지 않았다. [확실]

## 1. 화면 진단 줄 (표시 전용, 코드 사실)

- `live_demo.py`의 영상 왼쪽 아래에 세 줄이 있다: 최근 3초의 fps와 max gap(`FrameRateMeter`), 카메라가 알려 주는 해상도와 fps, 최근 3초의 read, proc, det 평균과 읽기 실패 횟수 bad(`StageTimeMeter`). 모두 메모리 목록뿐이고 파일로 쓰지 않으며, 알람에 쓰는 시각(`arrival`, `time.monotonic`)은 바꾸지 않는다. 단위 테스트는 233개가 통과했다. [확실]
- read는 `capture.read()` 대기 시간, proc는 읽은 직후부터 규칙과 알람 계산이 끝날 때까지의 시간(`draw_ui`, `imshow`, `waitKey`는 포함하지 않음), det는 `detector(gray, 0)` 호출 시간이다. 화면에서 읽는 max는 read의 최댓값만 있다. [확실]
- 읽기가 실패하면 루프가 `break`로 끝나므로 bad는 사실상 항상 0이다. 실패한 읽기의 시각은 `FrameRateMeter`에 들어가지 않는다. [확실]

## 4. 에이전트의 이전 읽기 전용 측정 요약 (K1~K4, 대화 보고, 파일 기록 없음)

K1~K4는 이 로그에 없던 내용이라 한 줄씩 적는다. 아래 절대 시간은 학습이 동시에 실행 중이던 시기에 측정되었을 수 있고 시점별로 확인되지 않았다. [미검증]

- 단계별 시간(영상 1080×1920, 폭 450 처리 시 450×800, 검출 성공 300프레임): detector 중앙값 264.032 ms, 단계 중앙값 합 308.733 ms(이론 상한 3.24 fps), 검출이 합의 약 86%였다. [확실] (측정)
- 웹캠 크기 환산(시간 전용, 처리 폭 450에서 모양 337×450): 단계 합 중앙값 레터박스 170.066 ms(5.88 fps), 얼굴 중심 4:3 잘라내기 138.868 ms(7.20 fps). 그냥 640×480으로 늘이면 300프레임 모두 검출에 실패했다. [확실] (측정)
- K1 GIL(한 스레드에서 dlib 호출 20번, 다른 스레드에서 정수 덧셈): 덧셈 횟수 감소 비율이 detector 85.684~89.909%, predictor 53.808~59.926%였다(3회 반복). 해석은 쓰지 않았다. [확실] (측정)
- K2 사각형 재사용(지연 1~8프레임 = 48.2~385.9 ms, 영상 하나, 연속 300프레임): 전체 검출 EAR과의 차이 평균 0.00092~0.00232, 최댓값 0.03057~0.03656이고 원본 최소 진폭 0.04 이상인 경우는 없었다. [확실] (측정)

- K4 코드 읽기: 메인 루프의 알람 경로에는 `sleep`, `join`, 동기 소리 재생이 없고, 락은 `SirenPlayer`의 `start`, `stop`에서 증가 연산 구간에만 쓰인다. 동기 재생과 `previous.join`은 재생 스레드에서만 실행된다. [확실]

## 5. C. 원인 판단

- 두 시기의 차이는 학습의 동시 실행 여부뿐이라고 사용자가 보고했다. 학습은 CPU 코어 4개를 사용 중이었다(사용자 보고, 에이전트 미측정). [확실] (사용자 보고)
- 원인 자원은 CPU 경쟁으로 추정한다. workers 등 구체 메커니즘과 GPU 관여 여부는 미확정이다. 학습을 다시 돌려 확인하지 않았으므로 인과는 미검증이다. [추측]
- dlib 얼굴 검출기와 predictor는 CPU에서 실행된다(GPU 경로 없음, 이전 측정에서 `DLIB_USE_CUDA`는 False). [확실]
- 4번의 절대 시간(검출기 264 ms, 웹캠 크기 합 139~170 ms)을 기준으로 한 속도 대책(이전 사각형 재사용, 별도 검출 프로세스)은 현재 필요하지 않다(Claude 추론, 사용자 확정 아님). 폭 축소는 EAR 평균 변화 약 0.013이어서 보류한다는 판단만 유지한다(대화 중 판단, 결정 아님, 미결). [확실]
- 알람 중 R 직후의 순간 상승은 학습이 동시에 실행 중일 때만 관찰되었고 현재는 재현되지 않는다. 원인은 미확정이다. [미검증]

## 6. D. 운용 조건

- 라이브 데모와 향후 HM-LSTM 도구는 학습 등 CPU를 많이 쓰는 작업과 동시에 실행하지 않는다. 화면의 fps와 단계별 시간 줄로 감시한다. (Claude 제안, 사용자 확정 2026-10-09) [확실]
- 규칙 알람은 프레임이 들어온 시각(`time.monotonic`)을 기준으로 하고 프레임 번호를 쓰지 않으므로 fps가 변해도 알람 시각 계산 방식은 바뀌지 않는다. 이 기존 사실은 유지한다. [확실]
